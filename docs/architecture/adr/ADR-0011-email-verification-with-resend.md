# ADR-0011: Email verification with Resend after commit

## Status

Accepted.

## Decision

New local accounts remain unable to authenticate until their email is confirmed. Verification tokens contain 256
bits generated by a CSPRNG; only their SHA-256 digest is persisted. Confirming one token consumes it and invalidates
the remaining tokens for that account in the same transaction.

Registration persists the account and verification token atomically and publishes an application event. A
Spring `AFTER_COMMIT` listener sends the message through a provider-neutral application port implemented by the
Resend HTTPS adapter. Provider failures cannot roll back registration. Resend idempotency keys are stable per
verification request.

## Consequences

- Registration no longer creates an access or refresh token.
- A crash after commit but before delivery can lose the in-memory event; the user-facing resend operation is the v1
  recovery path.
- The existing Expense outbox is not reused because it is bounded-context-specific and persisting a raw verification
  token in its payload would violate the token-storage rule.
- If delivery volume or reliability requirements grow, email delivery will move to a cross-context outbox with
  encrypted transient delivery material, retries and terminal failure handling.
